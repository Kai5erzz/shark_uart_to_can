# CAN Monitor 往返性能测试

2026-10-31，Asia/Shanghai。本轮完成上位机与分析仪回传功能，并通过外部CAN实板测试；未修改或重新烧录MCU固件。

本报告是 **USART2 专用 RAW 双向透传改动之前的历史基线**，保留当时的真实测量。当前固件及新 RAW 测试页的主机验证见 [验证记录](validation.md)，不能将这里的 USB 测量作为新固件 USART2 的实板结果。

## 实测结论

低载1000次全部成功，平均RTT **1.450 ms**，P99 **1.861 ms**。间隔0.75 ms、窗口8的10000次测试全部成功，有效往返约 **1017次/秒**。突发窗口增大后出现超时，窗口16本次约1985次有效往返/秒、超时2.77%；这是过载边界测试结果，不能用作无丢帧能力指标。

这些数值覆盖整条主机往返路径。当前未接入CH340/USART2适配器，本次结果仅代表**SHARK原生USB CDC**入口；不能作为UART单向转发性能、MCU单向延迟或产品最大吞吐的结论。

## 设备与方法

| 项目 | 本次配置 |
|---|---|
| SHARK | `/dev/ttyACM1`，0483:5740，序号2066346F3042 |
| CAN Monitor | 达妙旧CDC USB-CAN，`/dev/ttyACM0`，2e88:4603，序号00000000050C |
| CAN | Classical，1 Mbit/s，外部TJA1044链路 |
| 串口配置 | 921600 8N1；USB CDC的实际传输速度由USB链路决定 |
| SHARK运行状态 | `mode=usb-can`，ID1，CAN正常模式 |
| 测试请求/回复 | 标准ID 0x6E0 / 0x6E1，每帧8字节 |
| 数据关联 | 4字节随机session标记 + uint32小端序号 |
| 超时/预热 | 200 ms；每项预热10帧，不计样本统计 |
| 运行入口 | SHARK测试引擎 + CAN Monitor无GUI回传，两个独立主机进程 |
| 固件版本边界 | INFO不提供构建指纹，本轮未确认当前运行镜像的Debug/Release与SHA256 |

```mermaid
flowchart LR
    H[SHARK主机测试线程] -->|USB CDC| S[SHARK]
    S -->|CAN 0x6E0| A[达妙分析仪]
    A -->|USB串口| M[CAN Monitor接收回调]
    M -->|立即提交回复| A
    A -->|CAN 0x6E1| S
    S -->|USB CDC| H
```

起点为主机调用串口write之前，终点为完整匹配回复从串口read返回之后，计时使用同一主机的 `time.monotonic_ns()`，不经过GUI消息队列。包含主机调度、驱动、两次CAN传输以及分析仪回传。

窗口表示最多未完成请求数；间隔0表示有空位就发送。发送延迟后不集中补发，电脑调度会使实际速率低于按配置间隔计算的理想值。P50/P95/P99采用nearest-rank，仅统计有效回复；超时、拒绝、取消另计。有效帧率=有效回复数/测量时长，包含等待最终回复或超时的时间，有效返回载荷速率=帧率×8；不是CAN物理线速。

## 实测数据

除第一项外均经过外部CAN。RTT单位ms；“未收到”均为200ms超时，所有项目入队拒绝、重复、迟到、解码错误、配置恢复错误均为0。

|---|---:|---:|---:|---:|---:|---:|---:|
| USB ECHO基线（10ms/1） | 1000/1000 | 0 | 0.458 | 0.642 | 1.043 | 2.007 | 96 |
| CAN低载（10ms/1） | 1000/1000 | 0 | 1.450 | 1.736 | 1.861 | 2.545 | 96 |
| CAN连续（0/1） | 2000/2000 | 0 | 1.093 | 1.290 | 2.206 | 7.138 | 874 |
| CAN突发（0/2） | 4999/5000 | 1 | 1.210 | 1.812 | 3.785 | 13.792 | 1532 |
| CAN突发（0/4） | 2988/3000 | 12 | 1.321 | 1.741 | 3.478 | 12.656 | 1678 |
| CAN突发（0/8） | 2963/3000 | 37 | 1.368 | 1.752 | 2.808 | 9.784 | 1908 |
| CAN突发（0/16） | 2917/3000 | 83 | 1.465 | 1.992 | 4.004 | 8.974 | 1985 |
| CAN限速（1ms/8） | 5000/5000 | 0 | 1.195 | 1.452 | 3.370 | 15.391 | 863 |

## 超时定位与固件计数

两批CAN测试合计42000个正式请求、90个预热请求。Monitor收到 **42090** 个请求，提交 **42090** 个回复，发送接口错误0；分析仪串口TX报告也为42090，串口解码丢弃与残包均为0。

SHARK各项 `can_tx_sent` 增量等于正式请求数加10个预热，说明去程请求已经提交并被Monitor接收。存在超时的各项，SHARK `can_rx` 增量恰好少了对应数量：

| 场景 | SHARK CAN_TX增量 | SHARK CAN_RX增量 | 缺少 |
|---|---:|---:|---:|
| 窗口2 | 5010 | 5009 | 1 |
| 窗口4 | 3010 | 2998 | 12 |
| 窗口8 | 3010 | 2973 | 37 |
| 窗口16 | 3010 | 2927 | 83 |
| 0.5ms限速 | 10010 | 9981 | 29 |

所有测试SHARK USB `rx_drop/tx_drop/parse_err` 无新增，`can_drop/fifo_lost/busoff` 无新增，TEC/REC为0。`can_tx_err=2990` 是测试前已有累计值，本轮没有增长。窗口16的两个UART报告出口分别新增 `tx_drop=245` 字节，其余项目未新增；两个UART仍以ASCII广播CAN报告，突发时其输出队列出现拥堵，不能算作USB接收丢帧。

证据将超时范围缩小到**回复提交之后、SHARK的CAN接收计数之前**。主机提交成功和分析仪TX报告不能独立证明物理总线上的每帧都成功到达。尚需抓取CAN总线、分析仪硬件发送队列状态和SHARK控制器接收事件，才能区分分析仪过载与SHARK接收环节；本轮没有据此修改MCU固件，也未把它归因于某一端。

测试结束恢复原CAN状态与端口报告格式，未保存Flash。最后观察到空闲堆4992 B、任务stack水位404个32位字（约1616 B）。这只代表本次负载下读到的余量。

```bash

  --rounds 10000 --interval-ms 0.75 --window 8 \
  --output build/performance/repeat-075ms.json
```

## 自动验证范围

SHARK的C主机测试（ASan/UBSan）与原Python回归通过；新增测试覆盖乱序、错误ID/标记/扩展帧、重复、迟到、拒绝、超时、取消、Ctrl+C、恢复配置和JSON/CSV导出。Tk+PTY集成验证性能页完成、取消、断开与串口reader交接，以及原有定时发送。最终SHARK共21项Python测试，其中6项为本轮新增性能相关测试，包含统计长行回归。

CAN Monitor共27项测试通过，覆盖官方串口发送fixture、过滤以防回传循环、失败计数、SDK ABI、SocketCAN线格式，以及真实Tk界面启用/断开和计数保存。SDK与SocketCAN发送通过模拟验证，实板仅验证旧CDC分析仪。

本轮同时修复主机接收解码器的长度限制：固件 `stats` 回复超过191字节，原助手会将其丢弃；host回复解析上限现为1023，固件命令限制仍为191。固件单向延迟、CH340/USART2入口、长期压力、掉电/USB重插等项目尚未由本报告验证。
